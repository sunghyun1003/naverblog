# 남아 있는 원고 번호 재정렬

## 사용자 요청과 적용 결과

사용자가 원고 일부를 삭제한 뒤 현재 남은 원고 번호를 1부터 다시 매겨 달라고 요청했다. 기존 ‘번호 고정’ 정책은 유지하되 이번에만 명시적으로 초기화했다.

- 삭제 반영 후 남은 운영 원고: 23개.
- 이전 번호 22~44 → 현재 목록 아래부터 1~23.
- 다음 신규 원고 번호: 24.
- 위/아래 버튼으로 저장한 목록 순서, 원고 ID, 제목·본문·이미지·심의필·발행 기록은 변경하지 않았다.
- 이후 삭제나 편집·재배포가 자동으로 번호를 다시 매기지는 않는다. 이번 초기화는 예약 작업이 아니다.

## 실행과 안전장치

대시보드 공개 API나 화면 버튼을 추가하지 않고 인증된 GitHub 수동 운영 작업으로 처리했다. PostgreSQL 지침에 따라 외부 호출을 DB 트랜잭션 밖에 두고, 짧은 잠금·시간 제한과 팀 범위를 사용했다.

1. [미리보기 40649946241](https://github.com/sunghyun1003/naverblog/actions/runs/40649946241): 조회만 수행. 운영 목록 23개와 기존 번호 확인.
2. [적용 40650618007](https://github.com/sunghyun1003/naverblog/actions/runs/40650618007): 확인한 목록·번호표의 지문과 일치할 때만 번호표 한 행 변경. revision 5 → 6.
3. 같은 트랜잭션에서 `audit_logs.action=content_numbers_reset`에 변경 전/후 번호표를 기록했다. 복구가 필요하면 이 기록을 기준으로 별도 승인 후 처리한다.
4. 저장한 번호표를 다시 읽어 검증한 뒤 확정했다. 적용 중 충돌·기록 실패·검증 실패 시 전체 작업을 취소한다.
5. [재확인 40650978364](https://github.com/sunghyun1003/naverblog/actions/runs/40650978364): 읽기 전용, `changed=false`, 23개, 다음 번호 24, revision 6 유지.

작업 코드 `3ed7500`을 main에 푸시했다. [운영 배포 40649920008](https://github.com/sunghyun1003/naverblog/actions/runs/40649920008)과 [회귀 검사 40649919961](https://github.com/sunghyun1003/naverblog/actions/runs/40649919961)이 성공했다. 로컬 전체 대시보드 198개, PC 임시저장 12개 테스트와 타입 검사·빌드도 통과했다.

브라우저 저장 캐시에 이전 번호가 잠깐 남아 있으면 콘텐츠 목록 새로고침으로 갱신한다. 실제 로그인 브라우저를 조작하거나 삭제된 원고를 다시 업로드하지 않았다.
